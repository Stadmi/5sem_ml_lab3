# Предрегистрация ЛР3 — до первого оценочного запроса

Дата подготовки: 2026-11-18. Прогноз предложен с помощью LLM.
19.11.2026 студент через диалог подтвердил прогноз «подтвердится» для всех
H1/H5/H10 и разрешил только бесплатные квоты GigaChat/Groq и активный грант
Яндекса, без покупки пакетов и перехода на платные тарифы.
Самостоятельная проверка эталонов студентом остаётся необходимой для защиты.
Протокол фиксируется коммитом, затем `freeze_protocol()`. После заморозки
код запрещает менять задачи, конфигурацию моделей, пилот, рубрики и этот документ.

## H1, группа 1: изменённые числа

Прогноз: подтвердится. На исходных задачах точность выше.
Восемь заранее определённых пар A01/F01 ... A06/F06, A07/F11, A08/F12. Исходные задачи —
учебные шаблоны, адаптированные из методички; это не доказательство
присутствия именно этих текстов в обучении моделей.
Для каждой модели: разность accuracy исходных и изменённых задач,
парный бутстреп 1000 повторов, exact McNemar. При n=8 мощность очень низкая:
невыявленную разницу нельзя объявлять отсутствующей.
Поддержка: положительная разность и p после Holm < 0.05.
Отрицательная значимая разность противоречит гипотезе. Иначе данных недостаточно.

## H5, группа 2: размер модели

Прогноз: подтвердится. Разрыв между большими и локальной моделью больше
на A, чем на B.
Только основные независимые задачи A и B. Для каждого типа сначала
усреднить correctness трёх больших моделей на каждой задаче, затем вычесть
correctness локальной модели. Статистика: gap_A - gap_B.
1000 стратифицированных по типу бутстреп-повторов задач с сохранением
всех моделей одной задачи вместе. Поддержка: 95% ДИ целиком > 0;
противоречие: целиком < 0; иначе данных недостаточно.
Это сравнение конкретных моделей, а не причинное доказательство влияния размера.

## H10, группа 3: калибровка

Прогноз: подтвердится. На A/B/F средняя заявленная уверенность выше accuracy.
Для каждой модели: среднее confidence/100 - correctness,
ECE по пяти фиксированным интервалам [0,.2), [.2,.4), ... [.8,1],
диаграмма надёжности. Группировать связанные пары A/F при бутстрепе.
Не включать E: её 100 строк не должны подавлять результаты учебных задач.
Отсутствующую уверенность не заполнять; указывать покрытие.
Поддержка: 95% ДИ разности целиком > 0; противоречие: целиком < 0;
иначе данных недостаточно. Четыре модельных анализа обозначаются разведочными.

## Общий протокол

- 37 записей: A=8, B=6 (3 true / 3 false), C=5, D=5, E=1, F=12.
- E — одна спецификация отдельного эксперимента, не 300 независимых учебных задач.
- 5 пилотных задач не входят в оценку. Отладка на всех четырёх моделях.
- Русский основной прогон, одна задача — новый независимый запрос.
- По результатам пилота к ЕДИНОМУ системному промпту всех моделей добавлен
  официальный soft-switch Qwen `/no_think`: API `think=false` у загруженного
  шаблона не отключал длинные рассуждения. Это отладка на исключённых пилотах,
  до первого оценочного запроса. Источник: https://huggingface.co/Qwen/Qwen3-4B
- Soft-switch и проверенный alias не гарантировали отсутствия рассуждений
  в `/api/chat`. Эти пилотные результаты сохраняются, но не используются
  для оценки. Выбран прямой `/api/generate` с `raw=true` и официальным
  одноходовым шаблоном Qwen3 для system/user. Завершающий think-префикс
  закрывается пустым, как в
  `tokenizer.apply_chat_template(enable_thinking=False)`. Веса остаются
  исходными Qwen3-4B Q4_K_M, без дообучения. Шаблон и digest входят в
  замороженный протокол. System/user-тексты у всех четырёх моделей
  одинаковы. Если модель всё равно рассуждает или обрывает ответ,
  это фиксируется как наблюдаемое поведение, не исправляется после оценки.
  Источник шаблона:
  https://huggingface.co/Qwen/Qwen3-4B/raw/main/tokenizer_config.json
  Документация raw: https://docs.ollama.com/api/generate
- При разборе ответа исключается блок до последнего `</think>`, в том числе
  если открывающий тег уже был в нативном шаблоне. Исходный текст сохраняется.
  Оборванные ответы (finish_reason=length/max_tokens/TRUNCATED) считаются
  невалидными, даже если внутри незавершённого рассуждения встречалась строка ОТВЕТ.
- temperature=0 либо заранее записанный минимум. Не менять режим после ошибки.
- Две независимые слепые оценки C/D; κ < .6 требует уточнения рубрик
  и повторной оценки, с отдельной регистрацией отклонения от протокола.
- Для B автоматически оценивается метка, вручную — качество обоснования 0–2.
- Для A/F числовые ответы: заданные rtol/atol; многокомпонентные ответы
  верны только при правильности всех компонентов. Недостаточность данных —
  отдельная правильная метка, не ошибочный отказ.
- Полная точность: бинарная по задачам, C считается верной только при балле 2,
  D — только при успешном первом запуске, допустимом результате и отсутствии
  методологических нарушений у обоих проверяющих.
- Основная общая точность считается по 36 учебным задачам, без E.
  Не рассчитывать общую точность, пока нет всех ответов и ручных оценок.
- ДИ общей точности: требуемый обычный бутстреп задач 1000 раз и дополнительный
  кластерный бутстреп связанных A/F. seed=42.
- Попарные сравнения 4 моделей: exact McNemar, p и Holm p по шести сравнениям.
- E: sklearn breast_cancer, 100 фиксированных тестовых строк со стратификацией,
  вложенные наборы 5 ⊂ 20, оба класса в каждом. Одни индексы для всех моделей
  и baseline. Положительный класс — злокачественная опухоль (исходный target=0).
- E: 0/5/20 примеров, новый запрос на каждую тестовую строку. LogisticRegression
  и GaussianNB на тех же 5/20; DummyClassifier по частому классу train20.
  Основные метрики F1 положительного класса и balanced accuracy; accuracy дополнительно.
- E: для ограничения длины контекста имена всех 30 признаков перечисляются один
  раз, а каждую строку представляет текстовый массив значений в этом порядке.
  Округления, отбора признаков и изменения масштаба нет. Такое представление
  одинаково для всех LLM. Вариант с повторением длинных имён в каждой строке
  не оценивался. Влияние сериализации на качество — ограничение эксперимента.
- При разборе результата пустой ОТВЕТ не заполняется содержимым следующей
  строки УВЕРЕННОСТЬ. Это исправление парсера выявлено только на пилоте.
- GigaChat: `precached_prompt_tokens` прибавляются к uncached prompt_tokens
  для физического объёма входа; исходный usage сохраняется отдельно. Для
  стоимости нужно явно указать правило учёта кэша и официальный тариф.
- Некорректные ответы E учитываются как ошибки, отдельно указывается valid rate.
- Исходные ответы записывать в append-only JSONL немедленно. Сохранять usage,
  effective model/version, параметры, длительность и ошибки, не сохранять секреты.
- Перед вызовом записывается событие started, после — ok/error с тем же request_id.
  В анализ входят только полученные ответы ok; started позволяет обнаружить
  внешнее прерывание. Успешные ответы не запрашиваются заново при возобновлении.
- Заголовки x-ratelimit учитываются до очередного запроса; ожидание ограничено
  90 секундами. При HTTP-ошибке/исчерпании квоты прогон останавливается,
  тариф не меняется, покупок нет. Историю повторов сохранять.
- Первый логический ответ — pass@1. Повтор после HTTP-ошибки разрешён отдельным
  явным запуском с логированием ошибки; не повторять валидные неверные ответы.
- Не интерпретировать стоимость бесплатного использования как стоимость API=0.
  Применять официальный тариф с датой и курсом валют при необходимости.
- `tariffs.json` — отдельные датированные исходные данные анализа, а не
  параметры генерации. Он может дополняться официальными ценами после прогонов;
  каждое изменение фиксируется коммитом с источником. Используется номинальная
  цена без скидок кэша; это не фактическое списание с бесплатного лимита/гранта.
- Код D не исполняется автоматически на основной машине: только в отдельной
  одноразовой VM/контейнере без секретов и сети. Таймаут процесса — не песочница.
- Не подменять отсутствующие результаты синтетическими.
